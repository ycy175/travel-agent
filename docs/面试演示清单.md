## 1. 短板一：并发改造 —— "不是删了把锁，是懂框架才敢删"

### 一句话引入

> "原代码每个请求 `synchronized(builder)` 新建 Agent、结束就 close。我改成单例了，但不是简单删锁——我先反编译确认了框架的线程模型。"

### 操作 1：亮出根因证据（30 秒，最加分）

```bash
CORE="C:/Users/Lenovo/.m2/repository/io/agentscope/agentscope-core/2.0.4/agentscope-core-2.0.4.jar"
javap -p -classpath "$CORE" io.agentscope.core.ReActAgent | grep -iE 'ConcurrentHashMap|slotKey|callSerializationKey'
```

指给他看：

- 三个 `ConcurrentHashMap`：`stateCache` / `slotVersions` / `permissionEngineCache`
- `callSerializationKey()` 返回 `slotKey(userId, sessionId)`

**话术**：

> "框架内部按用户+会话隔离状态、同一会话自己串行——它是为'单实例多会话'设计的。全局锁本来就多余。而且 `agent.close()` 会关掉 MCP 客户端，原代码每请求 close 一次反而是 bug。"

### 操作 2：跑单例契约测试（1 分钟）

```bash
DEEPSEEK_API_KEY=test-key ./mvnw -B -ntp -Dtest=AgentSingletonTest test
```

预期：`Tests run: 2, BUILD SUCCESS`。

**话术**：

> "这两个测试锁定'应用级单例'契约，谁把 bean 改回 prototype 或恢复逐请求 build，CI 立刻红。"

### 追问防守

| 追问 | 回答要点 |
|---|---|
| 为什么不按会话缓存多个 Agent？ | 框架自己按 session 分片，多建实例纯浪费内存，还重复连 MCP 子进程 |
| 同一会话并发两个请求怎么办？ | 框架 `callSerializationKey` 保证同会话串行，状态一致性由框架负责 |
| 单例会不会串用户数据？ | 状态存在按 `(userId, sessionId)` 分片的 ConcurrentHashMap，工具身份仍由 RuntimeContext 注入 |

## 2. 短板二：Agent 质量评测 —— "改 Prompt 不是凭感觉"

### 一句话引入

> "Agent 项目最大的问题是改了 Prompt 不知道效果有没有退化。我把它拆成护栏回归和模型质量两层。"

### 操作 1：跑评测，看结构化报告（1 分钟）

```bash
DEEPSEEK_API_KEY=test-key ./mvnw -B -ntp -Dtest=AgentQualityEvalTest test
```

预期输出 14 条 `[PASS]` + `结果: 14/14 通过` + `BUILD SUCCESS`。

**话术**：

> "14 个用例分三类：Prompt 安全契约、工具 Schema 越权、差标决策边界。CI 每次提交都跑，不用真实模型、不花钱。"

### 操作 2：★ 杀手锏 —— 现场把 Prompt 改坏，让它变红

先把 `src/main/resources/prompts/travel-orchestrator-v1.txt` 第 3 条里的
`禁止调用 book_travel` 改成任意别的文字，然后重跑同一条命令。

实测输出：

```
[FAIL] P01  Prompt 必须禁止在审批未通过时下单 -> Prompt 缺少锚点: 禁止调用 book_travel
结果: 13/14 通过
BUILD FAILURE
```

**话术**：

> "看——我把'禁止在审批未通过时下单'这条规则删了，评测立刻抓到、CI 变红。这就是 Prompt 外置 + 契约评测的价值：改话术不再是拍脑袋，有回归网兜着安全底线。"

**演示后务必恢复**（我已实测此流程，工作区可干净复原）：

```bash
git checkout -- src/main/resources/prompts/travel-orchestrator-v1.txt
git status --short    # 应为空
```

### 追问防守

| 追问 | 回答要点 |
|---|---|
| 为什么不直接测模型回答？ | 模型输出概率性、要 API Key、不稳定；护栏是确定性底线，必须先守住。模型质量作为发版前第二层 |
| 14 个用例够吗？ | 用例在数据文件 `agent-eval-cases.json`，加用例不用改代码；真实项目按线上 badcase 持续补充 |
| 护栏和模型质量怎么分工？ | 护栏层每次提交都跑、守住安全底线；模型层发版前跑、衡量体验质量 |

## 3. 共同叙事线（收尾用，体现思路一致）

> "这两件事本质是一回事——**都是把'靠约定、靠感觉'变成'靠代码和测试兜底'**。并发上不信任'应该没人并发 build'，用单例 + 测试锁定；Agent 上不信任'改 Prompt 应该没问题'，用评测集锁定。这跟整个项目'LLM 不可信、服务端兜底'的设计原则是一脉相承的。"
