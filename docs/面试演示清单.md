## 1. 短板一：并发改造 —— "不是删了把锁，是懂框架才敢删"

### 一句话引入

> "原代码每个请求 `synchronized(builder)` 新建 Agent、结束就 close。我改成单例了，但不是简单删锁——我先反编译确认了框架的线程模型。"

### 操作 1：亮出根因证据（30 秒，最加分）

```bash
CORE="C:/Users/Lenovo/.m2/repository/io/agentscope/agentscope-core/2.0.4/agentscope-core-2.0.4.jar"
javap -p -classpath "$CORE" io.agentscope.core.ReActAgent | grep -iE 'ConcurrentHashMap|slotKey|callSerializationKey'
```

指给他看：

- 三个 `ConcurrentHashMap`：`stateCache` / `slotVersions` / `permissionEngineCache`
- `callSerializationKey()` 返回 `slotKey(userId, sessionId)`

**话术**：

> "框架内部按用户+会话隔离状态、同一会话自己串行——它是为'单实例多会话'设计的。全局锁本来就多余。而且 `agent.close()` 会关掉 MCP 客户端，原代码每请求 close 一次反而是 bug。"

### 操作 2：跑单例契约测试（1 分钟）

```bash
DEEPSEEK_API_KEY=test-key ./mvnw -B -ntp -Dtest=AgentSingletonTest test
```

预期：`Tests run: 2, BUILD SUCCESS`。

**话术**：

> "这两个测试锁定'应用级单例'契约，谁把 bean 改回 prototype 或恢复逐请求 build，CI 立刻红。"

### 追问防守

| 追问 | 回答要点 |
|---|---|
| 为什么不按会话缓存多个 Agent？ | 框架自己按 session 分片，多建实例纯浪费内存，还重复连 MCP 子进程 |
| 同一会话并发两个请求怎么办？ | 框架 `callSerializationKey` 保证同会话串行，状态一致性由框架负责 |
| 单例会不会串用户数据？ | 状态存在按 `(userId, sessionId)` 分片的 ConcurrentHashMap，工具身份仍由 RuntimeContext 注入 |

## 4. 概念澄清与改造作用（面试追问防守）

### 4.1 "解除全局锁"是不是加了连接池？—— 不是，是单例

这是最容易混淆的概念，一定要分清：

| | 连接池 | 本次改造（单例） |
|---|---|---|
| 资源数量 | 预先建好**多个** | 全程只有**一个** Agent 实例 |
| 使用方式 | 借出 → 归还 → 别人再借 | 所有人直接共用同一个 |
| 解决什么 | 频繁建立/销毁连接的开销 | 反复 build/close Agent 的开销 |

**并发能力不是靠"池化"来的**，而是 AgentScope 框架内部用 `ConcurrentHashMap` 按 `(userId, sessionId)` 隔离状态——同一会话自动串行、不同会话真并发。因为框架自己保证了分片隔离，才不需要那把全局锁。

补充：MCP 子进程本来就是启动时建一次、全局复用的（见 `AgentConfig`）。改造前的问题不是"没池化"，而是**每个请求结束都调用 `close()` 把共享资源关掉了**。这次是去掉那个错误的 close，让本就共享的资源真正活到应用退出。

### 4.2 "安全网"是什么？—— 评测 + CI 组成的保护机制（比喻）

"安全网"是比喻，不是技术名词。指：**改 Prompt 改坏了（比如删掉"禁止未审批下单"），评测立刻报红、CI 失败，问题被拦在上线之前**——像杂技演员下面的网，掉下来被接住，不会直接摔到生产环境。对应到项目就是 `AgentQualityEvalTest` + `ci.yml`。

### 4.3 "Agent 质量评测"是什么？—— 衡量 Agent 好不好的方法

传统软件用单元测试验证"输入 → 输出"的确定性结果；但 Agent 的输出是模型生成的、不确定，没法简单断言，所以需要专门的**评测（eval）**。本项目分两层：

- **护栏回归**（CI 每次跑）：Prompt 契约、Schema 越权、差标边界，14 个用例，守的是确定性安全底线；
- **模型输出质量**（需 API Key、发版前手动跑）：工具调用序列、事实一致性，衡量的是概率性的体验质量。

一句话：评测就是"用可重复的方式回答——这个 Agent 到底好不好、改完有没有变差"。

### 4.4 两个改造的作用（不改变功能，改变质量与能力画像）

| 改造 | 对系统 | 对面试 |
|---|---|---|
| 并发改造 | 解除全局锁→多会话真并发；修复每请求误关 MCP 客户端的隐藏 bug；不再反复 build 省资源 | 证明从"会用框架"到"懂框架"——反编译拿证据再动手 |
| Agent 评测 | Prompt 改坏立刻报警守安全；改话术有客观标准；AI 工程化 | 答好 AI 岗必问的"怎么评估 Agent 质量" |

**共同作用**：把"靠约定、靠感觉"变成"靠代码和测试兜底"——正是"LLM 不可信、服务端兜底"原则在两个层面的落地。
