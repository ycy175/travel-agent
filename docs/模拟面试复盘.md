# 模拟面试复盘

基于一轮 7 问的模拟面试整理。核心结论：**技术细节是懂的，但表达时经常把两层概念混为一层，或用错词**。面试判断"你到底懂不懂"，看的就是能不能把概念边界说清楚。

---

## 总评表

| 题 | 表现 | 关键问题 |
|---|---|---|
| 1. 项目介绍 | ⚠️ 弱 | 讲功能不讲痛点；选框架当核心决策 |
| 2. 工具越权 | ❌ 答偏 | 混淆"请求鉴权"和"工具参数越权" |
| 3. 审批绕过 | ⚠️ 半对 | 对象说错（订单 vs 审批单）；动作说错（提交审核 vs 抛异常） |
| 4. 幂等 | ⚠️ 背结论 | 只说唯一索引，漏了业务层查重、异常回查、FAILED 重试 |
| 5. 单例并发 | ✅ 满分 | 三个采分点全中，主动否掉连接池陷阱 |
| 6. 优先级判断 | ⚠️ 理由错 | 把一致性问题说成功能问题；没按概率×影响÷成本排序 |
| 7. 抗压辩驳 | ✅ 良好 | 抓住两个真亮点，但细节用词不准 |

## 第 1 问：项目介绍

**题目**：用两分钟讲清项目解决什么问题、你负责什么、最核心的技术决策。

**我的回答问题**：

- 讲功能不讲痛点——"解决出差全过程"是功能描述，不是问题；
- 职责模糊——"负责 agent 智能开发阶段"等于没说；
- **核心决策选错**——选 AgentScope 框架是工具选型，不是技术决策。真正的核心决策是"LLM 不可信，服务端兜底"，被藏起来了。

**示范答法**：

> "企业差旅以前靠人工：员工记不住差标、审批靠口头、Agent 直接下单有越权和重复下单风险。我做的是一套差旅 Agent 平台，覆盖查差标→起草审批→人工审批→合规下单→审计全链路。
>
> 我在里面负责 Agent 与业务后端的整合，包括工具设计、审批状态机、幂等和评测。
>
> 最核心的决策是**把 LLM 当不可信输入源**：它只提供业务参数，身份从会话注入，金额/权限/状态全部服务端二次校验。这个原则决定了后面所有设计——工具 Schema 不暴露 userId，下单前重新查审批状态，全链路写审计。"

**要点**：先讲问题 → 再讲角色 → 最后抛出一个能引出追问的设计决策。

## 第 2 问：工具越权

**题目**：Agent 调工具时，怎么防止模型自己填别人的 userId 冒充身份下单？

**我的回答**：说"会话隔离 + 登录 token 验证，token 不一致拒绝"。

**错因**：答的是**请求鉴权**（这个 HTTP 请求是谁发的），问的是**工具参数越权**（工具参数里填了别人的 userId）。这是两层——合法用户的 token 验证能通过，但模型仍可能在工具参数里填 lisi 的 userId。token 验证通过 ≠ 工具参数安全。

**示范答法**：

> "分两层。第一层是请求鉴权：HMAC Token 拦截 `/api/**`，确认请求是谁发的。但这挡不住工具参数越权——合法用户的 token 也可能被模型诱导填别人的 userId。
>
> 所以第二层在工具设计上：**身份参数不暴露给模型**。工具方法签名里身份是 `RuntimeContext`，框架注入，不进 JSON Schema；模型只能填行程、金额这类业务参数。我还写了 `ToolSchemaTest`，断言 Schema 里不能有 `userId`/`level`，防止后人改坏。这样模型即使被提示词诱导，也物理上没有填身份的入口。"

## 第 3 问：审批绕过

**题目**：Agent 说"审批通过了，帮你下单"，但审批单还是 PENDING，服务端怎么防？

**我的回答**：说"判断订单真实状态，PENDING 时提交人工审核"。

**错因（两处用词错误）**：

1. 查的是**审批单** `travel_approval` 的状态，不是订单状态——下单前根本没有订单；
2. 不会"提交人工审核"，而是**直接抛 409 异常拒绝**。提交审核是更前面 `submit_travel_approval` 工具的事。

**示范答法**：

> "完全不信任 Agent 的措辞。`OrderService.book()` 第一件事是按审批单号重新查数据库里的 `travel_approval`，状态必须是 APPROVED 或 BOOKED，PENDING/REJECTED 直接抛 409 拒绝。
>
> 而且不止状态：还要过差标校验、累计订单金额不能超过审批金额、审批单必须属于当前用户。这几道都是服务端自己算，跟 Agent 说什么无关。所以模型就算被诱导说'审批通过了'，也下不出去单。"

## 第 4 问：并发幂等

**题目**：同一审批单快速点两次下单，或 Agent 因重试调两次 `book_travel`，怎么保证不下出两笔？

**我的回答**：只说"一单一类型，数据库唯一索引兜底"。

**错因**：只背了结论，丢了机制，而且漏了最关键的一层——**FAILED 订单允许重试**。

**完整机制（四步）**：

1. 业务层先查 `findByApprovalAndType`，已存在且 BOOKED → 直接返回同一单；
2. 并发下两个请求都查到"没有"，都去 insert，唯一索引 `(approval_id, type)` 只让一个成功，另一个抛 `DuplicateKeyException`；
3. 捕获异常后**回查返回已存在订单**——这才是并发安全的闭环；
4. 已有订单是 FAILED 时，不是简单返回，而是把状态重置 CREATED 重新执行。

**示范答法**：

> "分业务层和数据库层。业务层先按 (审批单号, 类型) 查，有了且是 BOOKED 就直接返回，幂等命中。
>
> 但并发时两个请求可能同时查到'没有'，这时靠数据库的 `(approval_id, type)` 唯一索引兜底——只有一个 insert 成功，另一个抛 DuplicateKeyException，我们捕获后回查返回已存在订单，所以用户看到的是同一笔。
>
> 还有一层：如果之前那单是 FAILED（供应商失败），允许重试——把状态重置为 CREATED 再执行。所以幂等不是简单拒绝重复，而是区分成功/失败状态分别处理。"

## 第 5 问：单例并发（✅ 满分）

**题目**：改成单例后，多用户同时对话为什么不会串状态？是不是加了连接池？

**我的回答**：框架按 `(userId, sessionId)` 分片存状态，不同会话真并发、同一会话串行，没有加连接池。

**点评**：三个采分点全中，主动否掉陷阱。加分项：补一句证据链——"我反编译过 `ReActAgent`，内部是三个 `ConcurrentHashMap` 加 `callSerializationKey`，所以敢这么改"。

**要点**：面试时能分清易混概念，比多背十个知识点值钱。

## 第 6 问：优先级判断

**题目**：七条已知限制，给两周工期，优先改哪条？为什么？

**我的回答**：优先改"外部调用在事务内"，理由是"外部调用决定 Agent 核心功能好坏"。

**错因**：**把一致性问题说成了功能问题**。Mock 供应商本来就能下单成功，功能完全正常。这个问题解决的是失败场景的数据一致性——供应商扣款成功、本地事务回滚，导致用户被扣钱但系统没订单。它不影响功能好坏，影响的是出错时会不会丢钱。

**如果坚持选这条，正确论证**：

> "七条里只有这一条可能造成真实资金损失。所以我优先上本地消息表（Outbox）：下单先落消息表、事务提交后异步调供应商，失败由补偿任务重试，保证'扣款成功'和'订单落地'最终一致。"

但要扛住追问："这是修复成本最高的一条，两周够吗？供应商是 Mock，演示环境根本不暴露——为什么优先修当前不会发生的问题？"

**更好的答法（示范）**：

> "我选前端 token 存 localStorage。七条里绝大多数是'规模化之后才暴露'的问题——限流单机、单例 Agent、Mock 供应商，在单实例演示下都不会出事。但 token 存 localStorage 是**当下就存在的真实安全漏洞**：一旦有 XSS，攻击者直接拿 token 冒充用户调审批和下单接口，而我的系统里审批和下单是有资金后果的。
>
> 修复路径也清晰：改成 HttpOnly + Secure Cookie，加 CSRF Token，补一组越权测试。工作量两三天，剩下的时间把 CI 和回归测试补全。相比之下 Outbox 两周转开采不完，性价比不如先堵安全洞。"

**要点**：好答案不是选"最技术"的那条，而是按 **发生概率 × 影响严重程度 ÷ 修复成本** 排序，并主动交代"为什么不选其他"。

## 第 7 问：抗压辩驳

**题目**：你这个项目像"CRUD 套了个 Agent 壳"——把数据库操作包装成工具让模型调。用一分钟说服我。

**我的回答**：说了①会话记忆压缩，②二次确认防越权。

**点评**：抓住了两个真亮点，但两处用词不精确：

1. **"缓解数据库压力"** 错——上下文压缩压的是**发给模型的上下文长度**，目的是省 token、防超窗口；会话消息照样全量落库，跟数据库压力无关；
2. **"二次确认"** 应为**服务端不信任 Agent 的话、自己查一遍**——这不是"确认"，是校验；
3. 漏了最该说的**工具 Schema 层防越权**（第 2 问答过，没串进来）。

**示范答法**：

> "套壳是把 CRUD 包成工具让模型调，但我的难点在'LLM 不可信'下怎么保证系统正确——三点套壳做不到：
>
> 第一，**上下文压缩**：超过 30 条消息触发压缩、保留 10 条，把历史压成摘要再喂给模型。这解决的是长对话 token 爆炸和模型窗口限制，不是简单存数据库。
>
> 第二，**Schema 层防越权**：工具 Schema 里根本没有 userId、职级这些字段，身份由 RuntimeContext 注入，模型物理上没有冒充入口，还有 ToolSchemaTest 守住这个契约。
>
> 第三，**服务端二次校验**：模型说'审批通过了'没用，下单前服务端自己查审批单状态、差标、累计金额、归属，任何一条不满足就拒绝。模型可以生成任何文本，但绕不过这些规则。
>
> 所以 Agent 在我这里只负责'表达与规划'，所有状态、权限、金额都是服务端兜底——这是一个治理问题，不是把 CRUD 挂上去那么简单。"

---

## 最该练的三件事

1. **背熟核心原则**——"LLM 只负责表达与规划，身份/权限/金额/状态/幂等全部服务端校验"，任何技术点都往这句话上挂；
2. **区分易混概念**——请求鉴权 vs 工具参数越权、一致性问题 vs 功能问题、上下文压缩 vs 数据库存储、单例 vs 连接池；
3. **回答"为什么选这个"时**——按"发生概率 × 影响 ÷ 成本"排序，并主动交代"为什么不选其他"。

## 通用话术模板

**项目介绍**（两分钟版）：

> 痛点 → 我做了什么 → 我的职责（具体到模块） → 核心设计决策（能引出追问的那个）

**技术点回答**（任何一题）：

> 直接结论 → 具体机制（类名/字段名/异常类型） → 挂回核心原则"服务端兜底"

**优先级/选择题**：

> 按概率×影响÷成本选一个 → 说清修复路径 → 主动说明为什么其他条不选
